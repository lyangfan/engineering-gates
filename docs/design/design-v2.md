# engineering-gates v2 设计稿

> 状态：草稿，待用户确认（阶段 2）。日期：2026-10-14。
> 权威：`decisions.json`。本文每段标注所依据的决定编号；与登记冲突时以登记为准。
> 本文只组织已确认决定，不新增决定；尚待 spec 阶段确定的细节列在 §13。

## 1. 目标与范围

engineering-gates v2 覆盖完整开发链路：问答形成决策，决策组织为设计稿，设计稿切分为 spec，spec 经审查后实现，实现经审查后交付（D-001）。v2 自身的设计也按这条链路产生，本文即其阶段 2 产物（D-005）。

v2 的首要目标是在不同 harness、不同 LLM 上得到一致的流程结果。为此，凡能确定性判断的事都交给脚本，LLM 只承担判断与写作（D-015、D-018）；流程是否真的一致，用固定题库度量（D-019）。

v2 与 science-gates 保持独立，不共享代码（D-020）。

## 2. 角色

| 角色 | 职责 | 依据 |
|---|---|---|
| 用户（Decision Owner） | 回答问题并作决定；确认设计稿、spec 地图与档位；决定实质选择、不收敛后的重置和变更级别 | D-007、D-008、D-011、D-016、D-017 |
| 协调者 / 作者 | 组织问答、维护登记、写设计稿与 spec、推进状态 | D-006、D-018 |
| 测试作者 | 实现前只依据 spec 写验收测试；实现后编写错误实现补丁；裁定测试异议 | D-003、D-013、D-014 |
| 实现者 | 让验收测试通过；可补充自己的单元测试；不得修改验收测试 | D-003、D-013 |
| 审查者 | 在独立会话中按冻结检查表审查，只读 | D-004、D-016 |

独立性只要求不继承被审对象的产生上下文，不要求不同模型家族（D-004）。角色与模型能力的分工只作参考，可以全部使用高能力模型；不写具体模型名，每次派发用什么模型由当时的指示或 harness 默认决定（D-032）。参考如下（D-032）：

| 角色 | 参考能力 | 理由 |
|---|---|---|
| 问答与协调、spec 起草（尤其严格档）、独立审查、复盘 | 高 | 出错时没有机器能发现，典型失败是"看似通过" |
| 测试作者 | 严格档高，标准与轻量档一般即可 | 错误实现补丁检查能机械暴露漏洞 |
| 实现者 | 一般即可，严格档宜中高 | 冻结测试、补丁检查与阶段 8 审查兜底 |
| 记账与同步（登记、账本、引用） | 一般 | 漏改错引由追溯检查发现 |

其中最重要的一条是审查者不弱于其所审作者（D-032）。

## 3. 工件与权威

- **决策登记**（`decisions.json`）：已确认决定的唯一权威。讨论记录只用于追溯来源（D-006）。
- **设计稿**：手写叙述，每段标注决定编号（D-006）。
- **spec 地图**：每份 spec 的目标、依赖与档位（D-007、D-008）。
- **spec**：条款、验收与错误实现，带稳定 ID（D-009、D-010、D-011）。
- **事实登记**：F-xxx 条目与探针（D-012）。
- **验收测试与错误实现补丁**（D-013）、**测试异议记录**（D-014）。
- **审查报告与账本**（D-016）。
- **状态文件**：阶段、未关闭事项、阻塞点由 LLM 写；身份字段只由脚本写（D-015、D-018）。

机器读写的文件（决策登记、配置、事实登记、状态文件等）用 JSON，脚本只依赖 Python 标准库；面向用户阅读与确认的文件（设计稿、spec、spec 地图）用 Markdown（D-021）。

流程内产物的身份是 git commit。流程分支合并进 main 只用普通 merge commit，禁用 squash 与 rebase，保证被引用的提交号在合并后仍可到达（D-033）。采用本流程即授权在流程专用工作分支或 worktree 上做本地检查点提交；push、merge、发布仍须逐次授权。LLM 不计算、不抄写 hash（D-015）。检查点提交只在 `eg/` 开头的分支上进行，只提交明确列出的路径，尊重仓库钩子与已配置的提交者身份，没有改动时不产生空提交；命令为 `eg.py checkpoint` 与 `eg.py identity`（D-026）；其退出码、超时、部分路径无改动、已暂存内容保护与路径规则见 EG-S1 中引用 D-027 的条款；锁冲突的有界重试、失败恢复、超时终止、身份环境变量与退出码边界见引用 D-028 的条款。不在 git 中的外部大文件身份暂不实现，等第一个使用者出现时另立 spec（D-029）。每次检查点提交带运行标识，命令据此在并发时准确找到自己的提交；覆盖提交者身份的配置项同样被拒绝（D-030）。

## 4. 九个阶段

| # | 阶段 | 放行方式 | 依据 |
|---|---|---|---|
| 1 | 问答决策 | 登记格式与替代关系的机械检查 | D-006、D-007 |
| 2 | 设计稿 | 双向引用检查 + 用户确认 | D-006、D-007 |
| 3 | 切分与定档 | 决定分配检查 + 用户确认地图与档位 | D-007、D-008 |
| 4 | 写 spec（含现实核验） | 追溯与条款分类检查、探针通过 | D-010、D-011、D-012 |
| 5 | 审 spec | 独立审查（轻量档跳过，见下） | D-007、D-009、D-016 |
| 6 | 测试先行 | 测试在当前代码上先失败；测试冻结 | D-009、D-014 |
| 7 | 实现 | 验收测试通过、探针重跑、补丁检查 | D-009、D-012、D-013 |
| 8 | 审实现 | 独立审查（轻量档为合并审查） | D-007、D-009、D-016 |
| 9 | 复盘 | 用户确认升级建议 | D-019 |

阶段 1 的问答规则：每轮一题，选项互斥并说明代价与影响，讨论前先核对已有决定，只有用户明确接受的结论才登记，推翻旧决定时保留历史并标注替代关系（D-006）。

## 5. 定档（阶段 3）

流程分轻量、标准、严格三档，在切分 spec 时为每份 spec 定档（D-002）。每份 spec 回答一份带版本号的是/否清单：公共 API/wire、持久化 schema 或身份、并发/提交点/恢复、权限/安全/外部副作用、其他 spec 拥有的合同或公共登记表、未核验的外部行为。任一为"是"进严格档；全为"否"时，新增用户可见行为进标准档，否则进轻量档。每个"是"指向具体条款。Agent 提议，用户确认，可上调，下调须写明理由（D-008）。

三档差异（D-009）：

| | 轻量 | 标准 | 严格 |
|---|---|---|---|
| spec 形式 | 一页卡片 | 完整 spec，稳定条款 ID | 完整 spec + 影响登记与迁移说明 |
| 现实核验 | 不要求 | 实测所用依赖行为 | 实测并钉版本，脚本存档 |
| 测试证明力 | 测试先失败 | + 每个错误实现补丁使测试失败 | + 崩溃/并发/超时故障注入 |
| 独立审查 | 实现后一次合并审查，不过即升标准档 | 阶段 5、8 各一次 | 阶段 5、8 各一次，另加跨 spec 影响检查项 |
| 审查预算 | 1 轮 | 1 + 1 | 1 + 2 |
| 用户确认点 | 定档、最终验收 | 定档、spec 冻结、实现 PASS | 同标准 + 影响登记 |

审查预算见 D-016。

## 6. spec 条款与追溯（阶段 4）

每个条款带稳定 ID，并归入三类之一：引用决定（D-xxx）、引用事实（F-xxx）、标为 AUTHOR-CHOICE（D-011）。碰到 §5 清单任一触碰面的 AUTHOR-CHOICE 是实质选择，冻结前逐条交用户决定并登记；其余为局部选择，冻结时列清单交用户过目（D-011）。

每条验收带 ID，注明覆盖的条款，并至少写一个"必须失败的错误实现"；测试用与语言无关的标记引用验收 ID。追溯链由脚本从内容扫描重建，不手工维护矩阵（D-010）。

具体写法：条款 `**[<SPEC>-Cnn]**`，验收 `**[<SPEC>-ACnn]**`，错误实现 `[<SPEC>-ACnn-Wn]`，测试标记 `eg:ac <验收 ID>`；决定状态只取 active、superseded、withdrawn；统一入口 `python3 scripts/eg.py`，项目配置为根目录 `eg.json`（D-022）。追溯检查可用 `--spec` 只检查选中的 spec，使多份 spec 能处于不同阶段并行推进（D-023）；可用 `--root` 指定项目根目录，缺省为当前目录（D-025）。登记 schema、标记与代码排除、`eg.json`、spec 地图表格、条款与验收边界、退出码与报告格式见 EG-S2 中引用 D-024 的条款。

脚本检查（D-010）：

1. 分给该 spec 的每条 active 决定至少被一个条款引用；
2. 每个条款至少有一条验收；
3. 每条验收至少写一个错误实现，且至少有一个带其标记的测试；
4. 测试标记引用不存在的 ID 即报错；
5. 标准档与严格档：每个错误实现补丁打上后，带对应标记的测试必须失败。

## 7. 现实核验（阶段 4、7、8 前）

依赖的外部行为登记为 F-xxx：一句话陈述、钉住的依赖版本、可执行探针、期望结果断言。探针在写 spec 时、实现开始前、审实现前各跑一次；任一次失败按依赖漂移处理，停止并回到 spec。轻量档不要求（D-009、D-012）。

## 8. 测试作者与错误实现补丁（阶段 6、7）

验收测试针对 spec 定义的对外接口编写；实现者可自由补充单元测试，但不作验收证据。测试作者可见 spec、事实登记和实现开始前的代码库，不可见实现者会话与进行中的代码；实现者只读可见验收测试（D-003、D-013）。

验收测试在阶段 6 结束时冻结。实现者认为测试有误时提交异议（测试 ID、条款、理由），被异议测试搁置，其余继续；测试作者以新会话裁定，认同则改测试并记录新版本，不认同而实现者坚持则判为 spec 歧义，回到 spec 由用户决定（D-014）。

标准档与严格档在实现完成后，测试作者第二次介入，按 spec 中的错误实现描述在候选代码上写补丁；脚本逐个应用并运行对应测试，每个补丁都必须使测试失败（D-013）。

## 9. 独立审查（阶段 5、8）

审查者在独立会话中工作（D-004）。检查表只含机器判断不了的问题：条款对决定的忠实性、局部选择是否确属局部、补丁对错误实现描述的忠实性、遗漏的失败路径、测试异议处理是否合理等；审查开始前冻结（D-011、D-013、D-014、D-016）。

每条阻塞 finding 映射一个检查项并给出反例；Closure 只审改动影响范围，不新增标准；Closure 可由新会话执行，输入为前序报告与账本（D-016）。

预算耗尽仍有阻塞项时判为 NON_CONVERGENT：脚本按根因归类剩余 finding，用户选择新 Baseline、回到 spec、拆分 spec 或接受限制后继续（D-016）。

## 10. 冻结后变更

脚本对比新旧条款 ID 后分三级，agent 提议、用户确认，用户可上调（D-017）：

- 编辑性：条款与验收语义不变，只做机械检查并记录；
- 局部：不碰 §5 触碰面，按轻量档做一次合并审查；
- 实质：碰到触碰面或其他 spec，按原档位重审改动影响范围，脚本列出受影响的其他 spec 并逐份判断。

只改代码、不改 spec 的修复：先跑全部验收测试与补丁检查，再做一次轻量单轮审查（D-017）。

## 11. 跨 harness 交付

规则以一份压缩后的完整协议交付（目标约 300 行），配合状态文件；LLM 依据协议判断下一步并更新状态。机械检查由脚本执行，脚本不驱动流程走向。AGENTS.md、CLAUDE.md、`.cursor/rules`、Codex SKILL.md 只路由到同一份协议（D-018）。

由于流程走向依赖模型遵从度，更换模型或 harness 时用题库衡量遵从度（D-019）。

## 12. 复盘与题库（阶段 9）

每份 spec 周期结束时，脚本按根因汇总 finding，agent 提出升级建议（机械检查、检查项、协议措辞、§5 清单项），用户确认后以新版本生效；周期内检查表与清单不变（D-016、D-019）。

埋雷题库首批约 10 题，取自 science_agent 真实缺陷，例如 SPEC-02 空转 drift 测试、SPEC-04 回归绕过被修路径、SPEC-06 由 agent 自选的 Annotation 激活方式、SPEC-09 的 tag 事实假设。协议、检查表或清单升版本前在题库上比较新旧版本的抓到率与误报（D-019）。

## 13. 留给 spec 阶段的细节

以下内容不需要新的用户决定即可起草，但在 spec 中会表现为 AUTHOR-CHOICE，按 D-011 分流：

- 决策登记、事实登记、spec、状态文件、审查报告与账本的字段与文件布局（D-006、D-012、D-016、D-018）；
- 追溯扫描规则（D-010；写法已由 D-022 确定）；
- 局部选择清单格式（D-011）；
- 探针的运行与断言格式（D-012）；
- 补丁的存放、应用与回滚方式（D-013）；
- 测试异议记录格式（D-014）；
- 检查点提交的分支命名与提交信息约定（D-015）；
- 审查检查表的具体条目（D-016）；
- 新旧条款对比与变更分级脚本（D-017）；
- 协议正文与各入口文件（D-018）；
- 复盘汇总格式与题库题目结构（D-019）。

## 14. 对 0.1.0 的影响

- 0.1.0 只有 spec 与实现两门；v2 补上阶段 1—3 与阶段 9（D-001、D-007）。
- `decision_coverage.py` 检查的是 A1–A9/B1–B7 检查项齐全性；v2 中设计决定覆盖由 §6 的追溯检查承担（D-010）。
- 0.1.0 合同的 `requirements` 被限定为检查项本身；v2 中产品要求以 spec 条款与验收表达（D-010、D-011）。
- 0.1.0 的 `subject-<round>` 字节副本与自定义 digest 机制由 git 身份取代（D-015）。
- 0.1.0 默认预算 1+1；v2 按档位分预算（D-016）。
- 0.1.0 只有 Codex 入口；v2 入口文件统一路由到同一份协议（D-018）。
